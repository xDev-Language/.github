# xDev

xDev is a general-purpose programming language that combines the procedural and object-oriented paradigms, based on [xBase](https://en.wikipedia.org/wiki/XBase) syntax. The xDev compiler produces native executables directly: machine code is generated by [LLVM](https://llvm.org/) and linked by the [LLD](https://lld.llvm.org/) linker. As a result, xDev inherits the portability of LLVM and can be ported to any platform that LLVM supports. It also benefits from LLVM's multi-pass code optimizations.

## xDev and LLVM

The `xdev` compiler is a single executable. It embeds LLVM and the LLD linker, so building programs requires no other compiler or linker.

From a `.prg` file to a program:

1. The preprocessor expands `#include`, `#define` and `.ch` files.
2. A hand-written recursive descent lexer and parser build the syntax tree.
3. The compiler checks the types declared with `AS`. Calls within one file are checked at compile time; a call from another file is checked at run time when the typed function is entered.
4. The code generator produces LLVM intermediate representation (IR).
5. LLVM optimizes it with the standard `-O2` pass pipeline and generates machine code.
6. LLD links it with the runtime library into a finished program.

There is no p-code, no virtual machine and no interpreter to fall back on for cases that are hard to compile. The whole program is native code. That is why xDev deliberately has no constructs that would require compiling text at run time, such as the `&` macro or `PRIVATE` and `PUBLIC` variables. Code blocks `{|| }`, `LOCAL` and `STATIC` variables and parameters take over their sensible uses.

What this means in practice:

- **Types go straight to LLVM.** `INT32` is a 32-bit machine integer and `FLOAT` is a `double`. A variable without `AS` has the type `ANY` and behaves dynamically.
- **Overflow is an error, not a wrap-around.** Arithmetic on `INT8` … `INT64` and `UINT8` … `UINT64` uses LLVM instructions with an overflow flag (`llvm.sadd.with.overflow` and similar).
- **Exceptions cost nothing until they are thrown.** `BREAK` and runtime errors compile to `invoke` and `landingpad`, and the unwinding uses the platform's native unwind tables.
- **Static libraries without external tools.** `xdev a.prg b.prg -o mylib.a` writes the archive with the built-in LLVM archiver.
- **The intermediate code can be inspected.** `xdev -S -emit-llvm program.prg` writes the IR to `program.ll`.

## The heart of xDev

**A function call is a plain call by name.** The compiler turns every call of a named function into an external symbol, and the linker resolves its address at build time, exactly as in C. There is no function table at run time. A function written in `.prg` and a library function written in C share the same ABI, `void NAME( X_CALL_CTX *ctx )`, so the compiler cannot tell them apart. A missing function is a build error, not a runtime error.

**DLL functions straight from `.prg`.** A `DLL FUNCTION` declaration gives the types of the parameters and the result:

```xBase
DLL FUNCTION Sum( a AS INT32, b AS INT32 ) AS INT32 LIB "mathlib.dll"
```

The compiler checks the types and passes the values according to the C ABI. At build time it opens the DLL, checks its architecture and that the function is exported, and creates an import library for LLD, so a missing function is a build error. The system loader fills in the address when the program starts; there is no lookup by name in xDev code. When a C library has to call xDev code, the compiler generates a trampoline with the required C signature (`CALLBACK FUNCTION`).

**Values.** A typed variable is a plain machine value. An `ANY` variable is an `X_ITEM`: a dynamic value that can hold a number, text, a date, an array, a hash, a code block or an object. A number is always a plain `int64_t` or `double`, with no stored display format. Arrays, hashes and objects are reference-counted and managed by the garbage collector in the runtime library.

**Text is UTF-8, everywhere.** There are no code pages. The rule is simple: functions without `U` work on bytes (`Len()`, `SubStr()`), and the `U…` functions work on characters (`ULen()`, `USubStr()`, `UChars()`). A character here is a Unicode code point, so a letter with a combining accent counts as two.

**No runtime cost where the compiler is enough.** `ProcName()` and `ProcLine()` without an argument are constants filled in at compile time, and `PCount()` reads the argument count from the call context inline. None of them calls a runtime function or needs a call-frame stack. The forms with an argument, such as `ProcName( 1 )`, are not supported yet.

## How xDev links libraries

An xDev library is a plain static `.a` archive. It can be built from `.prg` files (`xdev a.prg b.prg -o mylib.a`), from C code, or from both.

- **One-command installation.** `xdev install mylib.a` copies the archive to the `lib/xdev` directory next to the compiler. `xdev install --list` shows the installed libraries and `xdev uninstall` removes one.
- **Linking without options.** Every time a program is built, all archives in `lib/xdev` go into one linker group together with the `libxdev.a` core. LLD takes only the objects the program actually uses, so an unused library does not make the program bigger.
- **One ABI.** A library function has the same ABI as a function from `.prg`, `void NAME( X_CALL_CTX *ctx )`. The program calls it by name and the linker resolves the address. Before every link, `xdev` checks the installed libraries itself: when two of them define the same function, it stops with an error naming both archives.
- **No extra DLL files.** A library that uses an external open source engine contains it statically in its own archive. The required system libraries are recorded in the object metadata, so the program needs no extra files and no manual linker options. Licenses of the bundled components are in `lib/licenses`.
- **Terminal (GT) drivers on demand.** The core contains no screen driver code. A program selects a driver with a line such as `REQUEST GTWVT`. That line is an anchor for the linker, and the driver registers itself when the program starts.
- **Constants in `.ch` files.** Every library has its own header file, e.g. `#include "xml.ch"`, installed together with the compiler.

## xDev libraries

**Entirely xDev's own implementation**, written from scratch, with no external code:

- `xgtwvt`: text terminal in a system window, with graphics and mouse support
- `xgui`: graphical user interface with native system windows and controls
- `xjson`: JSON encoding and decoding that keeps the order of keys
- `xxml`: reading, building and writing XML documents, finding elements by path
- `xmytiff`: graphical controls with an event loop, written in xDev
- `xqrcode`: QR code generation, versions 1–40, error correction levels L, M, Q and H
- `xrdd`: DBF tables with NTX and CDX indexes, memo fields and relations
- `xsvg`: SVG graphics creation, written in xDev
- `xtui`: text user interface with a table browser, forms, a text editor and a sidebar, written in xDev

**xDev's own API over a bundled open source engine.** The API, the types and the error handling are xDev's implementation; the engine is linked in statically:

- `xcurl`: network client for HTTP, HTTPS and other protocols
- `xgtglfw`: graphical terminal in a window drawn with hardware acceleration, running on multiple systems
- `xgtsdl3`: graphical terminal in a window, with audio playback and image loading
- `xhpdf`: PDF document creation
- `xopenssl`: SHA and MD5 digests, HMAC, AES and RSA encryption, digital signatures
- `xzlib`: data compression for other xDev libraries

## Syntax at a glance

xDev aims for one way to write one thing, and every exception to that rule is a deliberate decision. Most blocks are closed by exactly one keyword; only `SWITCH` and `BEGIN SEQUENCE` can also be closed by a plain `END`. In the notation below, `[ ]` marks an optional part and `< >` a place for your own expression or name.

### Loops

```xBase
DO WHILE <condition>
   ...
   [LOOP]
   [EXIT]
ENDDO

FOR <variable> := <start> TO <end> [STEP <step>]
   ...
   [LOOP]
   [EXIT]
NEXT

FOR EACH <variable> [, <variable2>] IN <collection> [, <collection2>] [DESCEND]
   ...
   [LOOP]
   [EXIT]
NEXT
```

`LOOP` moves on to the next iteration and `EXIT` ends the loop. `FOR EACH` walks an array, a hash or the bytes of a string; for UTF-8 characters use `FOR EACH c IN UChars( cText )`. Inside the loop the variable knows its position: `<variable>:__enumIndex` is the element number, `:__enumKey` is the key in a hash, and `:__enumIsLast` tells whether this is the last element. Assigning to the variable changes the array element.

### Conditions

```xBase
IF <condition>
   ...
[ELSEIF <condition>]
   ...
[ELSE]
   ...
ENDIF

DO CASE
CASE <condition>
   ...
[CASE <condition>]
   ...
[OTHERWISE]
   ...
ENDCASE

SWITCH <expression>
CASE <constant>
   ...
   [EXIT]
[CASE <constant>]
   ...
   [EXIT]
[OTHERWISE]
   ...
ENDSWITCH
```

`DO CASE` checks the conditions in order and runs the first one that is true. `SWITCH` compares one expression with constants and works as in C: without `EXIT`, execution falls through to the next `CASE`.

### Exceptions

```xBase
BEGIN SEQUENCE
   ...
   [BREAK [<expression>]]
[RECOVER [USING <variable>]]
   ...
END SEQUENCE
```

`BREAK` (or the `Break( <expression> )` function) leaves the block, even from deep inside called functions, and passes any value to the variable after `RECOVER USING`. A runtime error becomes an exception when the error block passes it on: `ErrorBlock( {| oError | Break( oError ) } )`.

### Procedures and functions

```xBase
[STATIC] PROCEDURE <Name>[( [<parameter> [AS <type>] [, ...]] )]
   ...
   RETURN

[STATIC] FUNCTION <Name>[( [<parameter> [AS <type>] [, ...]] )] [AS <type>]
   ...
   RETURN <value>

INIT PROCEDURE <Name>
EXIT PROCEDURE <Name>
```

A program starts at `PROCEDURE Main()`. `STATIC` limits visibility to one file. An `INIT PROCEDURE` runs before `Main()` and an `EXIT PROCEDURE` after the program ends. An argument prefixed with `@` (e.g. `Swap( @a, @b )`) is passed by reference, so the function can change the caller's variable.

### Classes

Classes can be built in two ways: in xDev and in C. Both create the same kind of class in the runtime library, so a program cannot tell one from the other, and a class from `.prg` can inherit from a class written in C.

A class in xDev:

```xBase
PROCEDURE Main()

   LOCAL oAccount := Savings():New( "Anna", 100 )

   oAccount:Deposit( 50 )
   oAccount:AddInterest()
   QOut( oAccount:owner, oAccount:Balance() )   // Anna 157.5

   RETURN

CREATE CLASS Account

   DATA owner AS STRING INIT ""

   METHOD New( cOwner, nAmount )
   METHOD Deposit( nAmount )
   METHOD Balance()

HIDDEN:

   DATA nBalance AS FLOAT INIT 0

ENDCLASS

METHOD New( cOwner, nAmount ) CLASS Account

   ::owner    := cOwner
   ::nBalance := nAmount

   RETURN Self

METHOD Deposit( nAmount ) CLASS Account

   ::nBalance += nAmount

   RETURN Self

METHOD Balance() CLASS Account

   RETURN ::nBalance

CREATE CLASS Savings FROM Account

   METHOD AddInterest()

ENDCLASS

METHOD AddInterest() CLASS Savings

   ::Deposit( ::Balance() * 0.05 )

   RETURN Self
```

`FROM` names the parent class and `::` refers to the current object. Members after `HIDDEN:` are accessible only inside the class; access from outside ends with a runtime error. A class can also have `CLASSDATA`, `CLASSMETHOD`, `ACCESS` and `ASSIGN`, `OPERATOR`, `DESTRUCTOR`, and `PROTECTED:` and `EXPORTED:` sections.

A class in C, through the `x_cls*` API of the runtime library. The window classes in `xgui`, for example, are built this way:

```c
X_FUNC( COUNTER )
{
   static X_CLASS_HANDLE s_class = 0;

   if( s_class == 0 )
   {
      s_class = x_clsCreate( 1, "COUNTER" );
      x_clsAddData( s_class, "VALUE", 1 );
      x_clsAdd( s_class, "INCREMENT", X_FUNCNAME( COUNTER_INCREMENT ) );
   }

   x_clsReturn( ctx, s_class );
}
```

- `x_clsCreate()` creates a class with the given number of fields
- `x_clsAddData()` and `x_clsAdd()` add fields and methods
- `x_clsAddParent()` sets the parent class

A program uses such a class exactly like a class from `.prg`: `Counter():Increment()`.

## History

The idea for xDev took a long time to mature. The goal was a compiler with xBase syntax that boldly brings new solutions and a new way of working instead of adapting to what came before. The familiar syntax stays, but everything underneath it is built anew.

The project was founded by [Rafał Jopek](https://harbour.pl/) in 2024. In 2026 it received the official name xDev, and the decisions that shaped its character were made:

- **Native code only.** No p-code, no virtual machine, no interpreter. The whole program goes through LLVM.
- **The courage to remove.** The `&` macro and `PRIVATE` and `PUBLIC` variables are gone, because they required compiling text at run time and prevented type inference. Code blocks, `LOCAL` and `STATIC` variables and parameters took their place.
- **Types where they make sense.** `AS` declarations with types of known size, overflow checking and explicit `CAST`. Untyped code keeps working alongside them unchanged.
- **One way to write one thing.** Every additional form of the same construct requires a deliberate decision.
- **A number is just a value, and text is UTF-8.** Numbers do not remember a display format, and there are no code pages.
- **C libraries straight from `.prg`.** `DLL FUNCTION`, structures and callbacks are written in xDev code, with no intermediate layer in C.

The compiler source code is closed for now. The author plans to publish it when it is ready.
